# Safe-Net: аудит перед отзывом профессора

Дата: 20 сентября 2026. Проверена версия `ae6d3463144a6cf0ebcc6ccbba9f0cd4ec8bd9da`, ветка `upd/portfolio-localization`. На старте рабочее дерево было чистым. Исходный код приложения не менялся; добавлены этот отчёт и доказательства проверок.

**Вывод:** проект уже можно содержательно обсуждать как инженерный прототип, но перед отправкой работающего демо нужно исправить безопасность зависимостей, скачиваемую сборку расширения, оценивание заданий и воспроизводимость запуска. Для исследовательского отзыва нужно отдельно показать доказательства качества детектора и обучения. Зелёные существующие тесты этих проблем не обнаруживают.

Применены `skill-finder`, `code-quality` (review), `security` (audit), `product` для приоритизации относительно цели. Режим: чтение кода, существующие тесты, ограниченные локальные HTTP/UI-проверки и синтетические воспроизведения с подменой БД/сети. Публичный сервер не атаковали, реальные письма не отправляли, базу не сбрасывали.

## Исправить перед внешним демо

### 1. [P1, блокирует публичное размещение] Уязвимая версия Next.js

**Доказательство:** `client/package.json:43–45`, lockfile и реально установленный пакет: Next.js **16.0.1**, React/React DOM **19.2.0**. Проект использует App Router и серверный рендеринг. Эта версия Next.js попадает под официальный advisory об RCE в RSC: [CVE-2025-66478](https://nextjs.org/blog/CVE-2025-66478). Эксплойт на машине не запускался; подтверждены версия и применимая архитектура. Нельзя считать исправлением обновление только до первоначальной 16.0.7: после неё были дополнительные исправления, в том числе [RSC DoS](https://react.dev/blog/2025/12/11/denial-of-service-and-source-code-exposure-in-react-server-components).

**Сделать:** обновить Next и совместимые React/React DOM до актуальной исправленной версии выбранной поддерживаемой ветки; обновить lockfile, пересобрать и повторно проверить advisory. Остальные dependency findings разобрать по достижимости, начиная с runtime. В CI добавить автоматическую проверку зависимостей. Не переносить механически число срабатываний сканера в оценку риска.

**Приёмка:** версия вне актуальных уязвимых диапазонов; build, проверки auth и основные UI-сценарии проходят. Если уязвимая сборка ранее была публично доступна, отдельно проверить развёртывание и необходимость ротации его секретов.

### 2. [P1] Сайт распространяет старую сборку расширения с нарушением приватности

**Доказательство:** `client/public/downloads/safenet-guard-chrome.zip`, SHA-256 `1240ec453712ccf0785bbd669c518fe3052fb3d1b540494f6fffad6346088343`. В архивном `background.js` установлено `intelEnabled: true`; отдельного `mlEnabled` нет. При синтетической навигации на чистом хранилище реально исполненный код архива вызвал `fetch` к `http://localhost:8000/predict` с полным исходным URL — включая username/password, query value и fragment. Fetch был подменён, реального сетевого запроса не было. Результат: [zip-privacy.json](evidence/zip-privacy.json).

Текущие source privacy tests проходят, а выдаваемый пользователю артефакт не содержит этих исправлений. Стандартный адрес назначения локальный; это не доказательство утечки стороннему оператору. Но автоматическая передача полных URL уже нарушает заявленные consent/redaction, а настраиваемый endpoint расширяет риск. В ZIP также отсутствуют `_locales`, хотя текущий исходник локализован.

**Сделать:** пересобрать ZIP после исправлений, выпускать его из того же CI commit, что и сайт, включить в проверку именно упакованный артефакт. Показывать версию, commit и checksum на странице загрузки.

**Приёмка:** свежая установка скачанного ZIP не делает ML/intelligence-запросов без согласия; при включении передаёт только предусмотренные очищенные данные; EN/RU доступны. `bun run build:ext` сам по себе этого не доказывает.

### 3. [P1] Смена email обходит подтверждение владения адресом

**Место:** `server/src/user/services/user.service.ts:72–74`, `server/src/auth/jwt.strategy.ts:54`.

Авторизованный пользователь передаёт новый email через профиль. Сервис не требует текущий пароль именно для этой операции и сохраняет прежний `emailVerifiedAt`. Изолированный вызов реального сервиса после ValidationPipe подтвердил: email изменён, отметка подтверждения сохранена, JwtStrategy принимает пользователя. Чужой существующий аккаунт это само по себе не захватывает, но система признаёт подтверждённым адрес, владение которым не проверяла.

**Сделать:** `pendingEmail` и отдельное подтверждение нового адреса; текущий подтверждённый email сохранять до завершения; потребовать недавнюю повторную аутентификацию. Уведомлять прежний адрес о смене. Проверить нормализацию и конфликт уникальности.

**Приёмка:** неподтверждённый новый email нельзя использовать как подтверждённый идентификатор; чужая занятая почта не вызывает необработанный 500.

### 4. [P1] Повтор одного ответа позволяет получить 100% и больше

**Место:** `server/src/learning/services/tests.service.ts:103–144`, `server/src/learning/dto/submit-test.dto.ts`.

Сервер считает элементы `answers`, не уникальные вопросы. На реальном сервисе с синтетической БД и реальной DTO-валидацией: один правильный ответ из пяти → **20%, fail**; тот же `questionId` пять раз → **100%, pass**; шесть раз → **120%, pass**. Прочие условия выдачи сертификата существуют, поэтому это не доказательство получения сертификата без всего курса. Но подделка оценки/факта прохождения подтверждена.

**Сделать:** отклонять повторные и чужие questionId; проверять разрешённые options и тип вопроса; вычислять результат по набору вопросов теста. Добавить ограничения БД для допустимого диапазона результата как дополнительную защиту.

**Приёмка:** дубликат получает 400; каждый вопрос влияет на результат ровно один раз; результат всегда 0–100.

### 5. [P1 для достоверности обучения] Симулятор принимает выделение всего письма

**Место:** `server/src/learning/answers/task-answer.evaluator.ts:78–88,102–109`.

`spansMatch` принимает вложение строки в обе стороны. Поэтому весь абзац, содержащий хоть один red flag, не считается false positive; он также находит все вложенные признаки. Синтетический вызов реального evaluator с обычным текстом вокруг двух угроз вернул `isCorrect: true`, оба flag найдены, `falsePositives: []`. Это противоречит обещанию README о невозможности пройти задание выделением всего подозрительным.

**Сделать:** оценивать интервалы в исходном тексте, ограничивать избыточно захваченную область и учитывать нормальный текст внутри выделения. Оставить разумный допуск к неточности мыши; одного запрета длинных строк недостаточно. Добавить проверки полного письма, одиночного символа и точного выделения.

**Приёмка:** выделение всего текста или одной частой буквы не проходит; точные и немного неточные корректные выделения проходят.

### 6. [P1, статически подтверждённая цепочка] Страница может инициировать добавление себя в trusted list

**Место:** `extension/src/app/content/index.ts:150–153,252–255`; `extension/src/app/background/index.ts:49–57`; `extension/src/features/analyze-url/model/analyze.ts:105–118`.

Кнопка `#safenet-trust-btn` находится в DOM проверяемой страницы; обработчик click без проверки происхождения события вызывает `TRUST_SITE`. Скрипт страницы может вызвать `.click()` после появления предупреждения. Background правильно берёт домен из sender.tab, но это не доказывает согласие человека доверять этому домену. После trust проверки пропускаются и score становится 0.

**Статус:** прослежено по коду; полноценное воспроизведение между page world и content script в установленном Chrome-расширении не выполнено.

**Сделать:** постоянное доверие подтверждать в UI, которым владеет расширение, отдельно от DOM сайта; ограничить допустимых отправителей привилегированного сообщения. `event.isTrusted` полезен как дополнительная защита, но не заменяет доверенный интерфейс.

**Приёмка:** скрипт страницы не меняет trusted list; намеренное действие пользователя в интерфейсе расширения работает.

### 7. [P2] TypeScript и Python выносят разные вердикты на одинаковых URL

**Место:** `packages/guard-core/src/model/score.ts:3–6`, `packages/guard-core/src/model/blend.ts:22–40`, `ml-service/app/model.py:64–69,150–187`.

| Синтетический вход, без посещения адреса | TS правила | Python правила |
|---|---|---|
| `https://192.0.2.1/` | 35 / suspicious | 35 / safe |
| `https://paypal-alerts.com/` | 43 / suspicious | 35 / safe |
| `http://2130706433/` | 55 / suspicious | 20 / safe |

Есть и расхождение порогов, и различия извлечения/взвешивания признаков. Проверка `test_parity.py` сравнивает списки брендов/символов, а не выходы scoring. Честное совпадение этих списков не подтверждает заявленную parity поведения.

**Сделать:** один контракт порогов и нормализации; общий golden corpus для TS, Python и расширения; сравнивать score, level и существенные сигналы. Проверять граничные значения 30/31/39/40/69/70/71 и необычные представления URL.

### 8. [P1 для демо] Quick start не обеспечивает рабочий вход профессору

**Место:** `README.md:60–83`, `package.json` script `setup`, `server/prisma/seed.ts:86–103`, nullable `User.emailVerifiedAt` и проверка в auth.

Seed создаёт demo/admin без `emailVerifiedAt`, тогда как login требует подтверждённый email. На свежей базе это делает объявленные демонстрационные аккаунты непригодными для обычного входа. Попытка войти локально реквизитами demo из README также дала 401; причина именно для существующей БД отдельно не установлена.

Кроме того, README не описывает создание env-файлов и двух обязательных разных JWT secrets; `setup` этого не делает. Seed удаляет учебные данные, прогресс и пользователей: его нельзя предлагать как безопасную повторную настройку существующей базы.

**Сделать:** отдельный безопасный сценарий чистого demo; в development явно создавать подтверждённые demo-аккаунты; в production запретить публичные учебные пароли. Описать env/config preflight и разрушительные действия. Предоставить профессору ограниченный learner-доступ без административных полномочий.

**Приёмка:** новый checkout + изолированная пустая БД → документированные команды → успешный login → урок → симулятор → тест. Проверить этот путь автоматически целиком.

## Следующие исправления и пределы безопасности

- **[P2] Отзыв access JWT после смены/сброса пароля.** `password-reset.service.ts:155–166` отзывает refresh sessions; `jwt.strategy.ts` не проверяет session version, passwordChangedAt или отзыв access token. Старый access JWT сохраняет доступ до expiry; текущий срок — один час. Исправление: session/token version или проверяемая сервером сессия, определённая политика logout/password reset. Это подтверждено кодом; реальные токены пользователя не использовались.
- **[P2] Начисление XP при параллельных ответах.** `progress.service.ts:121–165` отделяет проверку прошлой правильной попытки от записи награды; нет атомарного ограничения «одна награда на user/task». Изолированная проверка с заглушками выявила двойное начисление; PostgreSQL concurrency test не проводился. Нужен уникальный award record/атомарная операция и тест двух конкурентных запросов.
- **[P2, требует интеграционного теста] Конкурентный refresh.** `client/api/axios.ts` запускает refresh отдельно для каждого 401; сервер при повторном использовании refresh отзывает семью. Обновление нескольких dashboard-запросов после истечения access может само отозвать сессию. Нужна единая выполняющаяся refresh-операция и определённое поведение между вкладками. Это статическая гипотеза с конкретной цепочкой, не подтверждённый браузерный сценарий.
- **История секретов.** В истории есть `server/.env` с JWT secrets и PEM private key по пути `server/src/certificates/key.pem`. Исторические JWT secrets не совпадают с текущим локальным env. Использование этих ключей в других развёртываниях/актуальность сертификата не проверены. Не объявлять это текущим захватом системы. Подтвердить ротацию всех когда-либо использованных реальных ключей; одна очистка истории их не отзывает. Текущие heuristic-срабатывания относятся к документации/шаблонам и именам переменных, действующий секрет в них не установлен.
- **Покрытие CI.** Нужны HTTP integration/E2E для ролей, двух пользователей, жизненного цикла сессий, grading и скачиваемого ZIP. `bun run test` не включает обе privacy-команды, хотя CI их запускает отдельно. Проверить clean-clone CI с единым корневым lockfile и фиксированной версией Bun; локальные PASS не доказывают hosted CI.

## Что усилит отзыв профессора

1. **Понятный исследовательский вопрос.** Например: улучшает ли связка «объяснение → симуляция → объяснимое предупреждение» распознавание новых фишинговых примеров по сравнению с обычным учебным текстом? Это вопрос для проверки, не уже доказанная эффективность.
2. **Доказательства детекции.** Версионированный независимый набор URL, разделение по времени/доменам/источникам, отсутствие пересечений train/test. Сравнение rules-only, model-only и blend на одном наборе; precision/recall/FPR, confusion matrix, latency и разбор ошибок. Текущие 16 curated примеров этого не заменяют.
3. **Доказательства обучения.** После исправления grading — небольшой согласованный пилот с исходным тестом, новым тестом после обучения и отложенной проверкой. Измерять изменение результатов, время и ложные тревоги; не объявлять маленькую удобную выборку доказательством причинного эффекта.
4. **Ясно указанный авторский вклад.** В репозитории подключён сторонний BERT checkpoint `ealvaradob/bert-finetuned-phishing`. Отделить разработанные вами правила, симулятор, архитектуру, privacy и эксперименты от готовой модели. Не приписывать себе её обучение. Model card уже честно ограничивает чужие метрики — сохранить это.
5. **Материалы для быстрого отзыва.** Английская страница на 1–2 страницы: вопрос, схема системы, ваш вклад, результаты, ограничения; короткая запись демо; reproducible release; три конкретных вопроса профессору о методике и ценности проекта. В `docs/PRODUCT_HARDENING_PLAN.md` обновить устаревшие утверждения: там HttpOnly, email verification и rotation всё ещё перечислены как будущая работа, хотя код уже их содержит.

**Рекомендуемый порядок:** сначала пункты 1–6 и рабочий demo setup; затем единый scoring contract и сквозные тесты; затем воспроизводимый benchmark и английский reviewer pack. Добавление новых функций сейчас менее полезно, чем достоверные оценки, совпадение артефакта с исходниками и ясное описание собственного вклада.

## Воспроизведение и ограничения

Из корня репозитория после успешной сборки API:

```sh
NODE_PATH="$PWD/server/dist" node docs/audits/2026-09-20/evidence/reproduce.cjs
node docs/audits/2026-09-20/evidence/zip-privacy.cjs
```

Первый harness вызывает скомпилированный код с синтетическими Prisma-заглушками, второй исполняет background из скачиваемого ZIP с mocked browser/fetch. Они не обращаются к реальной БД/сети. Выводы привязаны к указанному commit; после исправлений сохранённые логи останутся историческим свидетельством.

Не проверены: production TLS/hosting/config, фактическая доставка email, восстановление backup, нагрузка/DoS, все IDOR-маршруты с двумя реальными аккаунтами, полноценная установка расширения, независимое качество BERT, мобильная/keyboard/screen-reader матрица, публичная доступность и безопасность ранее развёрнутых экземпляров. На основании этого аудита нельзя объявить весь продукт безопасным или сертифицированным.

**Сильнейшая сторона:** связанная учебная платформа, объяснимые правила и практическое расширение с уже работающей базой автоматических проверок.

**Главный риск:** проверенный исходный код, распространяемая сборка и заявленные результаты местами расходятся.

**Следующий шаг с наибольшей отдачей:** выпуск исправленной воспроизводимой demo-версии с честной проверкой качества и кратким английским пакетом для профессора.
